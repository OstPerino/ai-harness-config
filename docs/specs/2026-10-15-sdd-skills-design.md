# Свои скиллы SDD вместо superpowers — дизайн

**Задача:** [#001](../../issues/001-own-superpowers.md)
**Дата:** 2026-10-15
**Статус:** на ревью у владельца

## Зачем

SDD-процесс владельца обкатан в двух проектах, `telegram-from-scratch` и `work-frontend`. Он описан в их `.claude/context/sdd/README.md`: 120 и 118 строк, почти одинаковых. Плагин superpowers при этом работает поперёк процесса: его `using-superpowers` на старте сессии тянет модель в собственные brainstorming и subagent-driven-development, а те запускают безымянных `general-purpose` вместо агентов харнесса (`requesting-code-review/SKILL.md:34`).

Цель — процесс становится двумя скиллами харнесса. Проект хранит только свои отличия, в разделе `## SDD` своего `CLAUDE.md`. Новый проект получает SDD без копирования README. Новый стек (мобилка, десктоп, Rust) подключается строкой в таблице ролей.

## Граница

**Делаем**
- Скиллы `spec` и `sdd` с шаблонами в `sdd/references/`.
- Копии трёх скиллов superpowers 6.4.1 без изменений текста: `systematic-debugging`, `test-driven-development`, `verification-before-completion`.
- Два режима у `planner` («партии», «бриф»), правило остановки у `e2e-dev`.
- Обновление `issue-start` и `issue-done`, удаление `plan-feature`, отключение плагина superpowers.
- Перенос `telegram-from-scratch` и `work-frontend` на раздел `## SDD`.

**Не делаем**
- Параллельный запуск партий по умолчанию. Его можно включить в `## SDD`, но отдельной логики планирования параллельности нет.
- Хуки Claude Code, которые механически запрещают шаги. Процесс держится на скилле и файлах состояния; хуки — задача #007.
- Поддержку других LLM — #007.
- Переписывание существующих `frontend-dev`, `node-dev`, `devops-dev` и ревьюеров — #005.

## Решения

### ADR-1: два скилла процесса, а не один и не цепочка из шести
- **Контекст:** процесс состоит из диалога с владельцем (спека) и исполнения почти без него (партии).
- **Решение:** `spec` — диалог и спека; `sdd` — партии, ревью, интеграция.
- **Отвергнуто:**
  - один скилл — файл на 400+ строк, нельзя написать спеку без запуска конвейера;
  - цепочка мелких скиллов — каждый переход держится на том, что модель сама вызовет следующий. В superpowers процесс рвётся именно на таких переходах.
- **Последствия:** граница между скиллами — утверждённая спека. `sdd` не начинается без неё.

### ADR-2: настройки проекта — раздел `## SDD` в `CLAUDE.md`
- **Контекст:** проекты отличаются таблицей агентов, гейтом, веткой, трекером, режимом PR.
- **Решение:** раздел в `CLAUDE.md`, который и так грузится в каждую сессию.
- **Отвергнуто:** отдельный `.claude/sdd.md` — ещё один файл, который модель может не прочитать.
- **Последствия:**
  - агент в worktree `CLAUDE.md` не видит, поэтому нужные правила переписываются в бриф;
  - в рабочем репо, где `CLAUDE.md` в git и его видит команда, раздел пишется в `CLAUDE.local.md`. Claude Code грузит этот файл автоматически.

### ADR-3: одна SDD-ветка на фичу, партии вливает ведущий, один PR в конце
- **Контекст:** владелец работает так: ветка фичи → worktree партий от неё → ведущий вливает → PR.
- **Решение:**
  - ветка `sdd/<фича>` (в рабочих репо — по шаблону из `## SDD`) от основной ветки;
  - каждая партия идёт в worktree от текущей головы SDD-ветки;
  - мерж `--no-ff` в SDD-ветку делает ведущий;
  - PR в основную ветку — один, в конце.
- **Отвергнуто:** PR на каждую партию — лишний цикл CI и мержа на каждую партию.
- **Последствия:** конфликты между партиями решает ведущий. Он видит обе партии, а исполнители — нет. Вопрос владельцу — только когда конфликт меняет логику одной из партий.

### ADR-4: debugging, TDD и verification копируются без изменений
- **Контекст:** владельца устраивают эти скиллы. Плагин целиком мешает, а отключить отдельные его скиллы, насколько известно, нельзя.
- **Решение:** копии в `claude/skills/`, в начале файла — источник и версия. Правка только одна: ссылки `superpowers:<скилл>` → `<скилл>`.
- **Последствия:** обновления superpowers подтягиваются руками, сравнением с апстримом.

### ADR-5: тип репозитория спрашивается один раз и записывается
- **Контекст:** пет и рабочий репозиторий отличаются атрибуцией, режимом PR, тем, как скрываются артефакты, и шаблоном ветки.
- **Решение:** при первом `sdd` без раздела `## SDD` — один вопрос «рабочий или пет?» с предложенным ответом по пути (`~/Job/*` → рабочий). Затем раздел заполняется умолчаниями для выбранного типа, ты подтверждаешь.
- **Последствия:** дальше ни один скилл тип не угадывает, а читает раздел.

## Скилл `spec`

**Триггеры:** «давай сделаем X», «распиши план по #N», «сделай спеку», «хочу фичу…» — всё, что ловили brainstorming и `plan-feature`.

**Шаги**
1. Читает `CLAUDE.md` (с `## SDD`), `.claude/context/STATUS.md` и issue — через `gh` или Jira MCP, как указано в `## SDD`.
2. Оценивает размер. Задача на одну партию, и тело issue уже годится как спека → предлагает `issue-start` и заканчивает. Выбранный путь называет вслух.
3. Пересказывает понимание: что сказал владелец и что предполагается — отдельно.
4. Задаёт вопросы по одному, только те, что меняют дизайн.
5. Предлагает 2–3 подхода с рекомендацией — только при настоящей развилке.
6. Показывает дизайн по секциям и получает согласие на каждую.
7. `planner` в режиме «партии» получает согласованный дизайн и возвращает:
   - партии с исполнителем и ревьюером из таблицы `## SDD`;
   - зависимости;
   - список премисс («есть/нет в коде»);
   - флаг безопасности;
   - самокритику.
8. Ведущий собирает спеку по шаблону и сам перепроверяет премиссы грепом.
9. Владелец утверждает спеку. Если в `## SDD` стоит «issue на партию: да», ведущий предлагает создать их и создаёт только после «да».

**Шаблон спеки** (`.claude/context/specs/<фича>.md`):

```
Зачем — 2–3 строки
Что есть — проверено <дата>: | что | где | как использовать |
Граница — делаем / не делаем
Решения — ADR-блоки, только настоящие развилки
Партии — | id | имя | исполнитель | ревьюер | зависит от | issue | статус |
Приёмка — чекбоксы, у каждого способ проверки
Безопасность — нужен security-reviewer: да/нет, почему
Открытые вопросы
```

`plan-feature` удаляется, его триггеры переходят в `spec`.

## Скилл `sdd`

**Триггеры:** «запускай SDD», «погнали по спеке», «следующая партия», а также утверждённая спека.

### Первый запуск в проекте
Если раздела `## SDD` нет:
1. Вопрос «рабочий или пет?» с предложенным ответом по пути.
2. Определение стека, слоёв и команды гейта по манифестам.
3. Таблица на подтверждение.
4. Запись раздела. Куда именно — по ADR-2.

**Умолчания по типу**

| | Пет | Рабочий |
|---|---|---|
| PR | `ведущий` — открывает и мержит по команде владельца | `я` — ведущий готовит `pr.md` |
| Атрибуция | да | нет, если правила репо не говорят иначе |
| Скрыть артефакты | `.gitignore` | `.git/info/exclude`; `.gitignore` не трогать |
| Ветка фичи | `sdd/<фича>` | шаблон спрашивается (`feature/<KEY>-<slug>`) |

**В рабочем репо** перед первой партией скилл проверяет, что в `.git/info/exclude` есть:
- `.claude/context/`;
- `.claude/worktrees/`;
- `CLAUDE.md`, если он локальный;
- `CLAUDE.local.md`.

Перед каждым мержем партии скилл смотрит `git status`. Файл из `.claude/` в индексе → стоп.

### Состояние
- Колонка «статус» в таблице партий спеки: `todo → brief → work → review → fix → done`.
- Файлы партии: `.claude/context/sdd/<фича>/<партия>-{brief,report,review}.md`.
- После `/clear` скилл читает таблицу и продолжает.

### Цикл партии
1. **Бриф.** `planner` в режиме «бриф» заполняет шаблон, проверяет премиссы грепом на сегодня и переписывает правила из `CLAUDE.md` по списку «В бриф копировать». Ведущий утверждает; владельцу — сводка в одну строку. **Первый бриф фичи утверждает владелец.**
2. **Исполнитель.** Агент из таблицы, в worktree на ветке `<ветка фичи>-<партия>` от текущей головы SDD-ветки. Промпт — пути к брифу и отчёту. ID агента сохраняется для SendMessage.
3. **Гейт.** Ведущий гоняет команду из `## SDD` в worktree и читает полный вывод. Красный → тому же исполнителю; фикс-раундом это не считается. Два красных подряд → стоп.
4. **Ревью.** Ревьюер из таблицы получает бриф, отчёт и диапазон коммитов и пишет `<партия>-review.md`.
5. **Фикс-раунд, ровно один.** Critical и Important чинит тот же исполнитель через SendMessage, мелкое и очевидное — ведущий сам. Затем гейт и просмотр диффа правок. Повторного ревью нет.
6. **Слияние.** Мерж `--no-ff` в SDD-ветку, гейт на ветке после мержа, удаление worktree.
7. **`done`**, исполнитель освобождается.

### Финал фичи
1. Итоговое ревью по слоям по диффу `<основная>...<ветка фичи>`, формат `final-review-<слой>.md` с разделом «стыки». `security-reviewer` — при флаге в спеке или по просьбе владельца.
2. Находки → партия `fixes`: бриф → исполнитель → гейт → слияние, без ревью.
3. `pr.md`.
   - `PR: ведущий` — по команде владельца ведущий открывает PR и мержит его после зелёного CI;
   - `PR: я` — ведущий отдаёт команду открытия, остальное делает владелец.

   Без команды владельца PR не открывается ни в одном режиме.
4. Ведущий предлагает `project-checkpoint`.

### Правила остановки
Стоп и сообщение владельцу:
- премисса брифа не подтвердилась;
- исполнитель вернул «правок ноль» или «заблокирован»;
- два красных гейта подряд;
- конфликт при слиянии меняет логику партии;
- файл из `.claude/` попал в индекс рабочего репо;
- `e2e-dev` исчерпал 3 попытки на сценарий.

## Изменения в агентах

- **`planner`.**
  - Режим «партии»: вход — дизайн; выход — таблица партий, премиссы, флаг безопасности, самокритика.
  - Режим «бриф»: вход — спека и id партии; выход — заполненный `brief.md`.
  - Режим выбирается по брифу от ведущего.
  - Текущий формат «задач» заменяется партиями.
- **`e2e-dev`.** Не больше 3 попыток на сценарий, включая починку нестабильности. Дальше — стоп и чеклист ручной проверки: шаги, ожидаемый результат, где смотреть. Если в `## SDD` стоит «E2E: нет», агент не вызывается.

## Перенос проектов

- **`telegram-from-scratch` (пет)** и **`work-frontend` (рабочий):**
  - содержимое `sdd/README.md` → раздел `## SDD` плюс строка «процесс — скилл `sdd`»;
  - отличия проекта — в разделе. Например, в work-frontend мерж идёт в `epic-branch`;
  - исторические брифы, отчёты и ревью не трогаются.
- **work-frontend:** проверка `.git/info/exclude`.
- **Когда:** после завершения текущих сессий в этих проектах. Скиллы и агенты подхватываются на лету.

## Проверка

1. **Срабатывание.** Evals skill-creator с фразами «должен / не должен».
   - «распиши план по #12» → `spec`;
   - «следующая партия» → `sdd`;
   - «поправь опечатку в README» → ни один.
2. **Сухой прогон** на `ai-harness-config`: тесты для `install.sh` из #007, 2 партии. Полный цикл до `pr.md`. Находки прогона правятся один раз, повторный сухой прогон не делается.
3. **Боевой прогон** на фиче пет-проекта — критерий закрытия #001.

## Приёмка

- [ ] `spec` и `sdd` срабатывают на фразы из evals и не срабатывают на контрольные — отчёт evals.
- [ ] Ни один скилл процесса не запускает `general-purpose` для реализации или ревью — `grep -rn general-purpose claude/skills/{spec,sdd}` пусто.
- [ ] Первый запуск `sdd` в проекте без `## SDD` задаёт вопрос о типе и пишет раздел — сухой прогон.
- [ ] В рабочем репо артефакты SDD не попадают в `git status` — проверка на work-frontend после переноса.
- [ ] Сухой прогон прошёл до `pr.md`, файлы `brief/report/review` лежат по шаблонам.
- [ ] Плагин superpowers отключён, три скопированных скилла доступны — список скиллов в новой сессии.
- [ ] Боевой прогон на пет-проекте.

## Безопасность

`security-reviewer` для этой работы не нужен: изменения — в промптах и markdown-шаблонах. Действия наружу (PR, мерж, issue в трекере) скиллы делают только по команде владельца.
