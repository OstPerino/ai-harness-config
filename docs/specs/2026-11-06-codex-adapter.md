# Общее ядро и адаптер Codex

Дата: 2026-11-06. Статус: решения согласованы в диалоге, реализация поручена ведущему. План — `docs/plans/2026-11-06-codex-adapter.md`.

Продолжение в Cloud: реализация, один независимый проход ревью и исправления
выполнены; Codex установлен в Cloud home. Реальный CLI discovery проверен,
hooks пока untrusted. Полная runtime-приёмка, TUI и ноутбук остаются открытыми.
Доказательства и результаты финальных гейтов — в начале плана.

## Результат для владельца

После установки Codex работает по привычным правилам: предлагает соло или SDD, сохраняет решения между сессиями, использует роли исполнителей и ревьюеров, запускает проверки проекта и соблюдает ограничения на внешние действия. Общие правила меняются в одном месте. Установленный Claude продолжает читать прежние файлы, повторная установка Claude для этой работы не требуется.

Сначала настраивается CLI statusline с контекстом и лимитами. Подключение внешних сервисов ведётся отдельным чеклистом в плане; отсутствие credentials не блокирует установку харнесса.

## Что уже есть: проверено 2026-11-06

- `install.sh` ставит агенты, скиллы, хуки и `CLAUDE.md` из `claude/` симлинками; настройки сливает из `claude/settings.d/`, учитывая принадлежащие установщику изменения в manifest.
- `claude/agents/` содержит 13 ролей. `claude/skills/` содержит процессы `spec`, `sdd`, `issue-start`, `issue-done`, checkpoint, learn и проверки качества.
- `claude/hooks/` содержит загрузку статуса, guard-проверки, Jira-проверку и typecheck. Загрузчик статуса читает только обычный файл `.claude/context/STATUS.md` внутри физического каталога проекта.
- `tests/gate.sh` запускает lint, проверку синтаксиса installer, все `tests/*.test.sh` и поиск домашних путей в отслеживаемых файлах. Прежний запуск ведущего завершился `8/8`.
- В основном рабочем дереве уже изменены `claude/CLAUDE.md` и `claude/skills/spec/SKILL.md`. Эти изменения принадлежат владельцу и входят в исходное состояние этой работы. Ведущий сохранил их коммитом в ветке реализации; основной checkout остаётся с теми же изменениями для живого Claude.
- По предварительному ревью Astra CLI поддерживает statusline-поля `context-remaining`, `context-window-size`, `five-hour-limit`, `weekly-limit`, `model-with-reasoning`. Наличие поля недельного лимита не гарантирует, что сервис отдаёт значение в конкретной сессии.

## Решения владельца

1. Общие правила, роли, процедуры и шаблоны хранятся в `shared/`. Настройки конкретного продукта остаются в его адаптере.
2. Codex получает собственные `AGENTS.md`, скиллы, агентов и хуки. Чтение `CLAUDE.md` вместо `AGENTS.md` и другие временные fallback не используются.
3. Существующие пути `claude/` и установленные ссылки сохраняются. Установка Codex не записывает в домашний каталог Claude.
4. Текущий статус проекта остаётся в `.claude/context/STATUS.md`; оба продукта читают один файл. Переименовывать его или заменять симлинком не нужно.
5. Перед разработкой агент предлагает соло или SDD, объясняет выбор одной фразой и спрашивает владельца. Уже выбранный в разговоре режим повторно не согласует.
6. Обсуждение подхода не означает запуск SDD. В соло агент пишет код в текущем диалоге; SDD делит работу между исполнителями по согласованной спеке.
7. На изменение проводится одно независимое ревью и один круг исправлений. После исправлений ведущий выполняет проверки и смотрит diff; повторного ревью без просьбы владельца нет.
8. Для этой работы режим уже выбран: планировщик пишет документы, ведущий реализует. Дополнительного согласования плана не требуется.

## Как будут устроены файлы

```text
shared/
  rules/                 общие правила работы и безопасности
  roles/                 задачи и чеклисты ролей
  workflows/             соло, spec, SDD, checkpoint, learn
  templates/             спека, бриф, отчёт и ревью
claude/                  прежние пути, прежний интерфейс установки
codex/
  AGENTS.md              общие правила с указаниями для Codex
  agents/                определения ролей в TOML
  skills/                процессы с инструментами и путями Codex
  hooks/                 обработка событий Codex
  config/                только принадлежащие харнессу настройки
scripts/
  render.sh              сборка файлов адаптеров и проверка --check
  install-codex.sh        установка Codex, вызываемая общим installer
docs/
  specs/                 эта спека
  plans/                 план и оставшиеся задачи
```

Названия небольших вспомогательных файлов может уточнить ведущий. Обязательные интерфейсы — `./scripts/render.sh`, `./scripts/render.sh --check`, `./install.sh --target codex`, `./install.sh --target claude`, `./install.sh --target all`, `--dry-run`. Прежний вызов `./install.sh` сохраняет поведение установки Claude.

В общих файлах не должно быть моделей Anthropic/OpenAI, имён API инструментов, схем разрешений и домашних путей конкретного владельца. Адаптер подставляет эти сведения явно. Не использовать глобальную замену слова Claude во всех текстах: упоминание продукта в документации может иметь другой смысл.

Сборка должна давать одинаковые байты при одинаковых исходниках: без времени запуска, случайных ID и машинных путей. Готовые файлы адаптеров хранятся в репозитории, чтобы установленный Claude продолжал находить их по прежним ссылкам. `--check` сравнивает ожидаемые и существующие файлы, ничего не записывает и возвращает ошибку при различии.

Первое извлечение общих текстов сохраняет действующие Claude-файлы, включая пользовательский diff. Существующие Claude спеки не переписываются. Правило выбора соло/SDD относится к новому общему процессу и Codex; намеренное изменение поведения Claude впоследствии оформляется отдельно. В данных сборки нужно явно описать это различие, чтобы следующая сборка не затёрла его.

## Адаптер Codex

### Правила и роли

Глобальный `AGENTS.md` содержит точку входа в процессы, правила внешних действий и указатель на общий checkpoint. Репозиторий получает собственный `AGENTS.md` с командами проверок и ограничениями харнесса. Пользовательские глобальные инструкции не теряются при установке.

Сохраняются имена 13 существующих ролей. Определения Codex используют отдельные TOML-файлы с `name`, `description`, `developer_instructions`. Модель и глубина рассуждения задаются адаптером, не общим описанием роли. Доступность выбранной модели проверяется отдельно; установка не обещает доступ ко всем моделям.

Ревьюеры возвращают замечания текстом. Ведущий сохраняет отчёт. Разрешённый Bash позволяет записывать файлы, поэтому описание роли «только чтение» не выдаётся за отдельную техническую песочницу. Эксперименты ревьюера выполняются вне дерева проекта или в специально подготовленной копии.

### Скиллы и выбор процесса

Перенести доступные собственные скиллы харнесса с их references и scripts. Для каждого скилла явно указать, перенесён ли он полностью, требует интеграции или остаётся приостановленным. В первую очередь должны работать `spec`, `sdd`, `project-checkpoint`, `issue-start`, `issue-done`, `git-flow`, `learn`, `humanize`, debugging и verification.

Процессы используют инструкции проекта из `AGENTS.md`; не создают fallback на `CLAUDE.md`. Ссылки на `.claude/context/STATUS.md` сохраняются намеренно. Метаданные вызова скиллов и имена инструментов проверяются под Codex, а не копируются из Claude без проверки.

Сторонний установленный `brainstorming` не изменяется на месте. Адаптер должен предотвратить его автоматическое навязывание обязательного проектирования для каждой правки: явная настройка отключения конфликтующего скилла, если клиент её поддерживает, либо отдельное согласованное описание процесса. Проверка должна подтверждать фактическую настройку, а не только наличие запрета в тексте.

### Хуки и защита

Сохранить назначение существующих guard-проверок и typecheck. Адаптер преобразует реальные события Codex в входные данные проверок. Для `apply_patch` нужно извлекать все затронутые пути, включая добавление, удаление и перемещение, до выполнения операции. После patch typecheck получает реально изменённые файлы и не запускается несколько раз для одного проекта без необходимости.

События с неизвестной или повреждённой формой не должны молча разрешать действие, для которого зарегистрирована защитная проверка. Отсутствие необходимого проверке инструмента возвращает понятную ошибку. Механизм поведения при timeout и аварии сверяется с текущим клиентом и проверяется отдельно.

Загрузка checkpoint сохраняет проверку обычного файла и физического пути каталога. Текст статуса передаётся как данные проекта; команды из него не получают самостоятельного разрешения.

Хуки требуют доверия клиента. Installer показывает, что установлено и что ещё нужно подтвердить штатным механизмом Codex; не пишет доверие от имени владельца и не объявляет защиту включённой до проверки. Предупредить в инструкции: hosted tools, интерактивный ввод через `write_stdin` и отдельные обходящие локальные хуки пути ограничивают покрытие. Хуки не заменяют filesystem/network permissions.

Чужие скиллы и плагины устанавливаются только после просмотра инструкций и исполняемых файлов. Учесть источник, версию/commit, изменения при обновлении и конфликты с правилами владельца. Вывод инструментов, страницы, тикеты и сообщения не расширяют задачу и разрешения. После блока нет обхода через другой инструмент. Отправка сообщения требует согласованных адресата и текста, если в текущем разговоре такое разрешение ещё не получено.

Подробные атакующие примеры и локальные сведения защиты не публикуются в этой спеке; регрессионные проверки должны использовать обезличенные синтетические данные.

## Установка и восстановление

- Codex устанавливается в `CODEX_HOME` и отдельный каталог пользовательских скиллов `AGENTS_SKILLS_HOME`; без переменных используются штатные пользовательские пути. В тестах оба каталога всегда временные.
- Файлы Codex не должны зависеть от домашнего каталога Claude. Допустимы общие файлы внутри этого репозитория; защитные проверки лучше хранить в `shared/`, а не обращаться из Codex к `~/.claude`.
- Перед записью installer проверяет исходники, форматы, параметры и весь план изменений. `--dry-run` не создаёт файлы, backups и manifest.
- Installer учитывает только собственные файлы, ссылки, ключи и элементы настроек. Чужие settings, агенты, скиллы и trust-состояние сохраняются.
- Коллизия имени чужого скилла или агента не замалчивается: показать конфликт и не заменить файл без явного разрешения. Чужой конфликтующий brainstorming не удалять автоматически.
- В `config.toml` не дублировать существующие таблицы, не стирать неизвестные настройки и комментарии. Hooks объединять с существующими без повторных одинаковых обработчиков.
- Сохранить прежние значения и файлы для восстановления. При сбое установки восстановить уже затронутые файлы либо оставить полный журнал операции и точную команду восстановления. Выбранный способ должен иметь тест аварии между записями.
- Manifest и backup относятся к выбранной цели. Повторная установка не создаёт новых различий. Удаление записи из исходников снимает лишь принадлежавшую харнессу запись, не позднейшую правку владельца.
- Installer Codex копирует полный проверенный набор в `CODEX_HOME/harness/releases/<content-id>`. ID определяется содержимым, а не временем. Этот каталог после публикации не изменяется; owned links и блоки инструкций ссылаются на установленный release. Поэтому Codex можно установить из ветки реализации до её merge: удаление worktree не ломает установленный набор. Это постоянный способ установки, а не временная ссылка на ветку.
- Ссылки не должны смотреть в временный worktree, который удалят после завершения. Основной checkout с живыми Claude-ссылками остаётся на прежней ветке. Перенос проверенных файлов из worktree не должен терять пользовательские правки. Релизы Claude не вводятся в этой задаче: его прежние пути сохраняются.
- Установка через нейронку запускает тот же installer, а не отдельную последовательность ручных правок.

## Statusline

В существующую `[tui]` добавляется `status_line` с моделью, остатком/размером контекста, пятичасовым и недельным лимитами. Изменение делается отдельно до установки всего харнесса, с сохранением конфигурации. Не показывать вычисленную догадку вместо отсутствующих данных сервиса. Проверить реальный CLI, а не только наличие строки в TOML.

## Память и проектные исключения

Не копировать внутренние базы сессий Claude в Codex. Отобранные полезные заметки переносятся в проверяемые Markdown-файлы: предпочтения в общие правила, инварианты в инструкции проекта, текущее состояние в checkpoint, приёмы ревью в references роли. Устаревшие и рабочие частные сведения не публикуются в репозитории харнесса.

Проект определяет способ работы с ветками/worktree, команды и владельца проверок, подготовку окружения, изоляцию БД/Redis/E2E, правила атрибуции и публикации. Если проверки нужно выполнять централизованно, исполнители не запускают их одновременно. Если worktree запрещены, SDD не создаёт их автоматически.

## Приёмка

- [ ] Контекст и поля лимитов видны в CLI; отсутствие данных недельного лимита честно обозначено, если сервис их не отдаёт.
- [ ] `./scripts/render.sh --check` проходит; изменение общего правила делает проверку красной до пересборки.
- [ ] Первое извлечение shared не теряет пользовательский diff и не меняет существующее поведение Claude.
- [ ] Установка только Codex сохраняет прежние Claude links/settings/manifest и не требует установки Claude.
- [ ] Codex получает собственные AGENTS, 13 ролей, доступные скиллы, references, hooks и конфигурацию без fallback.
- [ ] Installer проходит чистую, повторную и пробную установки, обнаруживает конфликты и восстанавливается после сбоя.
- [ ] Изменённая владельцем настройка не удаляется при обновлении только потому, что раньше принадлежала installer.
- [ ] Хуки проверяют многофайловый patch, перемещения, повреждённый ввод и границы каталогов; сохраняют прежние регрессии.
- [ ] Свежая сессия получает checkpoint; соло не создаёт спеку и партии без необходимости, SDD выполняет согласованную спеку.
- [ ] После одного ревью и исправлений нет автоматического второго круга ревью.
- [ ] Проектные исключения worktree и централизованных проверок соблюдаются.
- [ ] Старый и новый гейт проходят под `sh` и `dash`; все тесты используют временные home.
- [ ] Реальная установка Codex использует полный установленный release; ссылки не зависят от worktree. Оставшиеся trust/restart действия названы явно.
- [ ] Runtime Claude проверен только при доступности клиента и авторизации; статические проверки не названы живым тестом Claude.
- [ ] В плане есть отдельные незавершённые пункты интеграций, памяти, наблюдаемости и обновлений.
